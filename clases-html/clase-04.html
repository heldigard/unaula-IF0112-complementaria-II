Contexto y Motivación

En IoT, la red es el puente entre sensores, actuadores y la nube. Elegir una tecnología incorrecta puede:

  • Duplicar costos
  • Agotar baterías rápidamente
  • Crear puntos ciegos de cobertura
Idea clave: No existe "la mejor red" universal. Existe la red adecuada para cada caso de uso.

Variables de Decisión

Ancho de banda ¿Cuántos datos se transmiten? 1 KB/día vs 1 GB/día

Protocolos de Aplicación IoT

Los protocolos de aplicación definen cómo se comunican los dispositivos IoT. A diferencia de HTTP (diseñado para la web), los protocolos IoT están optimizados para dispositivos con recursos limitados: poca memoria, bajo ancho de banda y necesidad de bajo consumo energético.

Protocolo Transporte Características Casos de Uso
MQTT TCP Pub/Sub, ligero, 3 niveles QoS Sensores, telemetría, IoT general
CoAP UDP REST-like, muy bajo consumo Dispositivos restringidos, LPWAN
HTTP/REST TCP Universal, on-demand APIs web, integración cloud

📡 MQTT: Message Queuing Telemetry Transport

¿Qué es MQTT?

MQTT (Message Queuing Telemetry Transport) es un protocolo de mensajería ligero diseñado específicamente para dispositivos con recursos limitados y redes inestables. Fue creado en 1999 por IBM para monitorear oleoductos vía satélite, donde el ancho de banda era extremadamente limitado y las conexiones poco confiables.

Hoy es el protocolo más usado en IoT, siendo el estándar de facto para comunicación entre dispositivos y plataformas en la nube como AWS IoT, Azure IoT Hub, y ThingSpeak.

Arquitectura Cliente-Servidor con Broker

MQTT utiliza un modelo Cliente-Broker (no Cliente-Servidor tradicional):

Componente Función Analogía
Broker Servidor central que recibe, filtra y distribuye mensajes Como una oficina de correo central
Publisher
(Cliente)		 Dispositivo que ENVÍA datos (ej: sensor de temperatura) Como quien envía una carta
Subscriber
(Cliente)		 Dispositivo que RECIBE datos (ej: app móvil, dashboard) Como quien se suscribe a una revista
Topic Canal de comunicación jerárquico (ej: casa/sala/temperatura) Como la dirección en un sobre

Ejemplo de flujo de comunicación MQTT:

    ┌─────────────┐                    ┌─────────────┐
    │  SENSOR     │                    │   MÓVIL     │
    │  (Publisher)│                    │(Subscriber) │
    │  ESP32      │                    │   App       │
    └──────┬──────┘                    └──────┬──────┘
           │                                  │
           │  Publica en:                      │  Suscrito a:
           │  casa/sala/temp                   │  casa/sala/#
           │                                  │
           ▼                                  ▼
    ┌─────────────────────────────────────────────────────┐
    │                    BROKER MQTT                      │
    │         (ej: mosquito, HiveMQ, AWS IoT)            │
    │                                                     │
    │  Recibe mensaje → Busca suscriptores → Entrega     │
    └─────────────────────────────────────────────────────┘

Niveles de Calidad de Servicio (QoS)

MQTT ofrece 3 niveles de garantía de entrega, cruciales para aplicaciones donde la pérdida de datos puede ser crítica:

QoS Nombre Garantía Cuándo Usar
QoS 0 At most once
(Al menos una vez)		 El mensaje se envía una vez, sin confirmación. Puede perderse. Sensores que envían datos frecuentes donde perder un dato no es crítico (ej: temperatura cada 5 seg)
QoS 1 At least once
(Al menos una vez)		 El mensaje se reenvía hasta recibir confirmación. Puede duplicarse. La mayoría de aplicaciones IoT (recomendado). Balance entre confiabilidad y rendimiento.
QoS 2 Exactly once
(Exactamente una vez)		 Garantiza entrega única con handshake de 4 pasos. Más lento. Aplicaciones críticas donde duplicados son inaceptables (ej: facturación, comandos de control)

Ejemplo Práctico: Envío de Temperatura

Escenario: Un ESP32 envía temperatura cada 10 segundos a un dashboard.

  • Topic: unaula/laboratorio/temperatura
  • Payload: {"temp": 24.5, "unidad": "C", "timestamp": 1708723500}
  • QoS: 1 (recomendado para telemetría)
  • Retain: true (el último valor queda guardado para nuevos suscriptores)
💡 ¿Por qué MQTT es ideal para IoT?
  • Header mínimo: Solo 2 bytes de overhead (HTTP tiene ~200+ bytes)
  • Desacoplamiento: Publisher y Subscriber no necesitan conocerse
  • Escalabilidad: Un broker puede manejar millones de dispositivos
  • Calidad de servicio: Garantías de entrega configurables

📡 CoAP: Constrained Application Protocol

¿Qué es CoAP?

CoAP (Constrained Application Protocol) es un protocolo diseñado específicamente para dispositivos "constrained" (restringidos): aquellos con muy poca memoria (10-100 KB), procesadores limitados, y redes de bajo ancho de banda. Fue estandarizado por el IETF en 2014 como RFC 7252.

A diferencia de MQTT, CoAP usa UDP en lugar de TCP, lo que lo hace más eficiente pero requiere manejar la confiabilidad a nivel de aplicación cuando es necesaria.

Modelo Request/Response (Estilo Web)

CoAP funciona como una versión minimalista de HTTP, usando el mismo modelo request/response que conoces de la web:

Característica CoAP HTTP (comparación)
Transporte UDP (sin conexión, rápido) TCP (orientado a conexión)
Tamaño header 4 bytes fijo ~200+ bytes típico
Métodos GET, POST, PUT, DELETE GET, POST, PUT, DELETE, etc.
Formato Binario (compacto) Texto (verbose)
Modelo Request/Response (1:1) Request/Response (1:1)

Características Clave de CoAP

✅ Ventajas
  • Ultra ligero: Funciona en dispositivos con solo 10 KB de RAM
  • Estilo REST: Usa URLs y métodos HTTP familiares
  • Observación: Permite "suscribirse" a recursos (similar a pub/sub)
  • Multicast: Puede enviar un mensaje a múltiples dispositivos
  • DTLS: Seguridad integrada (similar a HTTPS)
⚠️ Limitaciones
  • Sin broker: Cliente y servidor deben conocerse mutuamente
  • UDP: Requiere manejar pérdida de paquetes
  • Menos adoptado: MQTT es más popular en la industria
  • Sin QoS nativo: Debe implementarse manualmente

Ejemplo Práctico: Consulta de Sensor

Escenario: Un gateway consulta un sensor de humedad en una red LoRaWAN.

GET coap://[2001:db8::1]/sensors/humidity
Accept: application/json

Respuesta (4 bytes header + payload):
2.05 Content
{"humidity": 65, "unit": "%"}

MQTT vs CoAP: Comparación Detallada

Criterio MQTT CoAP
Modelo de comunicación Pub/Sub (muchos a muchos) Request/Response (uno a uno)
Capa de transporte TCP (confiable, más overhead) UDP (rápido, puede perder paquetes)
Requiere broker Sí (centralizado) No (peer-to-peer)
Garantía de entrega 3 niveles de QoS integrados Confirmaciones opcionales
Overhead por mensaje ~2-5 bytes ~4 bytes
Uso de memoria Medio (~100 KB mínimo) Muy bajo (~10 KB posible)
NAT/Firewalls Fácil (conexión saliente TCP) Difícil (UDP puede ser bloqueado)
Adopción industrial Muy alta (AWS, Azure, Google Cloud) Moderada (específico para LPWAN)

¿Cuándo usar MQTT vs CoAP?

Usa MQTT cuando:

  • ✅ Necesitas garantía de entrega (QoS 1 o 2)
  • ✅ Múltiples dispositivos necesitan los mismos datos
  • ✅ Dispositivos detrás de firewalls/NAT
  • ✅ Usas plataformas cloud (ThingSpeak, AWS IoT, etc.)
  • ✅ Conexión persistente es viable
  • 📍 Ejemplo: Monitoreo industrial, smart home, telemetría en tiempo real

Usa CoAP cuando:

  • ✅ Redes con ancho de banda extremadamente limitado (LPWAN)
  • ✅ Dispositivos muy restringidos (<100 KB RAM)
  • ✅ Comunicación simple consulta/respuesta
  • ✅ Necesitas multicast (un mensaje a muchos)
  • ✅ Redes UDP son confiables
  • 📍 Ejemplo: Sensores en LoRaWAN, redes 6LoWPAN, dispositivos NB-IoT
🎓 Para tu proyecto SMAI: Recomendamos MQTT (o HTTP) porque:
  • ThingSpeak soporta MQTT nativamente
  • ESP32 tiene bibliotecas maduras para MQTT
  • Mayor facilidad de depuración
  • Documentación y ejemplos abundantes

📚 Glosario de Abreviaturas y Términos

Es importante conocer el significado de las abreviaturas técnicas utilizadas en IoT:

Abreviatura Significado Completo Descripción Rápida
PAN Personal Area Network Red personal, corto alcance (hasta 10m)
LAN Local Area Network Red local, alcance medio (hasta 1km)
WAN Wide Area Network Red amplia, largo alcance (más de 1km)
LPWAN Low Power Wide Area Network Red de bajo consumo y largo alcance
BLE Bluetooth Low Energy Bluetooth de bajo consumo energético
MQTT Message Queuing Telemetry Transport Protocolo de mensajería ligero para IoT
CoAP Constrained Application Protocol Protocolo para dispositivos con recursos limitados
HTTP Hypertext Transfer Protocol Protocolo de transferencia de hipertexto (web)
REST Representational State Transfer Estilo de arquitectura para APIs web
API Application Programming Interface Interfaz para comunicación entre aplicaciones
TCP Transmission Control Protocol Protocolo de control de transmisión (confiable)
UDP User Datagram Protocol Protocolo de datagramas de usuario (rápido)
QoS Quality of Service Calidad de servicio en comunicaciones
