🎯 Desafíos de Comunicación en IoT

Aprendizaje clave

IoT enfrenta desafíos únicos: redes inestables, dispositivos con batería limitada, escalabilidad masiva y recursos computacionales restringidos. Los protocolos IoT como MQTT están diseñados específicamente para superar estas limitaciones.

📡 Conectividad

  • Redes inestables → QoS
  • Ancho de banda limitado
  • Alta latencia
  • Conexiones intermitentes

🔋 Energía

  • Batería limitada
  • Mínimo tiempo de transmisión
  • Wake-up frecuentes

📊 Escala

  • Miles a millones de dispositivos
  • Mensajes frecuentes
  • Muchos a muchos

🔒 Seguridad

  • Recursos computacionales limitados
  • Memoria reducida
  • CPU lenta

🌐 HTTP: El Protocolo de la Web

Modelo Request-Response

📤 CLIENTE (ESP32)

  • Inicia la comunicación
  • Envía GET /api/temperatura
  • Espera respuesta

📥 SERVIDOR (API)

  • Recibe petición HTTP
  • Procesa la lógica
  • Responde HTTP 200 OK

Flujo: Cliente → Request → Servidor → Response → Cliente

Características Clave

AspectoDescripción
IniciadorSiempre el cliente
ConexiónUna por petición (HTTP/1.1)
ModeloSíncrono (espera respuesta)
Push serverNo (requiere polling)
OverheadAlto (~800 bytes headers)

✅ Ventajas HTTP

  • Familiar y universalmente soportado
  • Debugging fácil (Postman, curl, navegador)
  • HTTPS integrado para seguridad
  • Infraestructura madura

❌ Desventajas para IoT

  • Overhead considerable
  • No soporta push del servidor
  • Polling consume batería
  • No ideal para tiempo real

📨 MQTT: El Protocolo Estrella de IoT

Aprendizaje clave

MQTT usa el modelo publish/subscribe con un broker intermediario. Esto permite desacoplamiento total: el publicador no necesita saber quién escucha, y el suscriptor no necesita saber quién publica. El broker enruta mensajes eficientemente.

MQTT - Protocolo diseñado específicamente para IoT por IBM en 1999.

Modelo Publish/Subscribe

🔄 BROKER MQTT

🔄

Centro de mensajes que enruta entre publicadores y suscriptores

📤 PUBLICADOR

Envía mensajes a topics
publish("casa/temp", "25.5")

📥 SUSCRIPTOR

Recibe mensajes de topics
subscribe("casa/temp")

✅ ¿Por qué MQTT para IoT?

  • Overhead mínimo (ahorro energía)
  • Push nativo (tiempo real)
  • Desacoplamiento (pub/sub)
  • Escalable (millones de dispositivos)
  • QoS garantizado
  • Retained messages
  • Last Will and Testament

🏷️ Topics (Temas) en MQTT

Aprendizaje clave

Los topics usan jerarquía con / como separador. Los wildcards + (un nivel) y # (múltiples niveles) permiten suscripciones flexibles. Esto es esencial para escalar sistemas IoT con muchos dispositivos.

Estructura Jerárquica

Usa / como separador para crear jerarquías:

casa/sala/temperatura
casa/sala/humedad
casa/sala/luz/estado
casa/cocina/temperatura
casa/cocina/luz
casa/dormitorio/temperatura

oficina/piso1/sala1/temperatura
oficina/piso1/sala1/humedad
oficina/piso2/servidor/cpu

edificio/sectorA/piso3/oficina12/aire

Wildcards (Comodines)

SímboloSignificadoEjemplo
+Un solo nivelcasa/+/temperatura
#Múltiples nivelescasa/#

Ejemplo de Wildcard +

casa/+/temperatura captura:

  • casa/sala/temperatura
  • casa/cocina/temperatura
  • casa/dormitorio/temperatura

Propiedades de Mensajes

PropiedadDescripción
PayloadContenido del mensaje (string, JSON, binario)
RetainÚltimo mensaje guardado para nuevos suscriptores
QoSQuality of Service (calidad de entrega)
Client IDIdentificador único del cliente
LWTLast Will and Testament (mensaje si se desconecta)

🎯 Niveles de QoS (Quality of Service)

Aprendizaje clave

QoS 0 (fire & forget) para datos frecuentes como temperatura. QoS 1 (at least once) para comandos importantes. QoS 2 (exactly once) para transacciones críticas como pagos. Mayor QoS = más overhead y latencia.

QoSNombreConfirmaciónUso
QoS 0 At Most Once
(Fire and Forget)		 ❌ Sin ACK Datos frecuentes, temperatura en tiempo real
QoS 1 At Least Once ✅ ACK (PUBACK)
⚠️ Posibles duplicados		 Comandos importantes, alarmas
QoS 2 Exactly Once ✅ 4-way handshake
❌ Sin duplicados		 Transacciones críticas, pagos

⚠️ Trade-off

Mayor QoS = Mayor confiabilidad pero también mayor overhead y latencia.

BateríaAlto consumoBajo consumo

¿Cuándo usar cada uno?

Usar HTTP cuando:

  • Integración con APIs web existentes
  • Comunicación ocasional
  • Actualizaciones de firmware (OTA)
  • Infraestructura HTTP ya existe

Usar MQTT cuando:

  • Muchos dispositivos (escala)
  • Comunicación tiempo real
  • Push desde servidor necesario
  • Dispositivos con batería
  • Alta frecuencia de mensajes

⚙️ Implementación MQTT en ESP32

Aprendizaje clave

La librería PubSubClient de Arduino es el estándar para MQTT en ESP32/Arduino. Implementa reconexión automática, callbacks para mensajes recibidos y soporta QoS 0 y 1. Los brokers públicos como HiveMQ permiten pruebas sin servidor propio.

💻 Factibilidad Windows: Arduino IDE es completamente compatible con Windows. Puedes compilar y cargar código en ESP32 desde Windows sin problemas.

🔧 Hardware: Si no tienes ESP32 físico, puedes usar simuladores gratuitos como Wokwi para probar MQTT con ESP32 virtual. El docente también puede hacer demostraciones en vivo con hardware físico.

Librería PubSubClient

Arduino IDE → Sketch → Include Library → Manage Libraries → Buscar "PubSubClient"

Código: Publicador MQTT

📥 Descargar .ino (Ejemplo HTTP/MQTT)

#include <WiFi.h>
#include <PubSubClient.h>

const char* ssid = "TU_RED";
const char* password = "TU_PASS";
const char* mqtt_server = "broker.hivemq.com";
const char* topic_temp = "unaula/sala/temperatura";

WiFiClient espClient;
PubSubClient client(espClient);

void setup() {
  Serial.begin(115200);
  WiFi.begin(ssid, password);

  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }

  client.setServer(mqtt_server, 1883);
}

void loop() {
  if (!client.connected()) {
    reconnect();
  }
  client.loop();

  // Publicar cada 5s
  static unsigned long lastMsg = 0;
  if (millis() - lastMsg > 5000) {
    lastMsg = millis();
    float temp = 25.5;
    char msg[50];
    snprintf(msg, 50, "%.1f", temp);
    client.publish(topic_temp, msg);
  }
}

void reconnect() {
  while (!client.connected()) {
    if (client.connect("ESP32Client")) {
      Serial.println("Conectado a MQTT");
    } else {
      delay(5000);
    }
  }
}

Suscriptor con Callback

void callback(char* topic, byte* payload, unsigned int length) {
  String mensaje = "";
  for (int i = 0; i < length; i++) {
    mensaje += (char)payload[i];
  }

  if (String(topic) == "unaula/sala/luz") {
    if (mensaje == "ON") {
      digitalWrite(LED_PIN, HIGH);
    } else if (mensaje == "OFF") {
      digitalWrite(LED_PIN, LOW);
    }
  }
}

void setup() {
  client.setServer(mqtt_server, 1883);
  client.setCallback(callback);
}

void reconnect() {
  if (client.connect("ESP32-Sub")) {
    client.subscribe("unaula/sala/luz");
  }
}

JSON en MQTT

#include <ArduinoJson.h>

void publicarJSON(float temp, float hum) {
  StaticJsonDocument<256> doc;
  doc["temperatura"] = temp;
  doc["humedad"] = hum;
  doc["timestamp"] = millis();

  char buffer[256];
  serializeJson(doc, buffer);
  client.publish("unaula/sala/datos", buffer);
}

📡 CoAP: Protocolo para Dispositivos Restringidos

CoAP vs HTTP

AspectoHTTPCoAP
TransporteTCPUDP
Overhead~800 bytes~10 bytes
FormatoTextoBinario

Ventajas CoAP

  • Overhead mínimo (~10 bytes)
  • UDP más ligero
  • Métodos similares a HTTP (GET, POST, PUT, DELETE)
  • Diseñado para IoT restringido

Métodos CoAP

MétodoUso
GETObtener recurso
POSTCrear recurso
PUTActualizar recurso

⚠️ ¿Cuándo usar CoAP?

  • Dispositivo < 100 KB RAM
  • Red limitada (6LoWPAN, ZigBee)
  • Overhead mínimo crítico
