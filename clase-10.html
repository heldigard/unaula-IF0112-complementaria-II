🎯 Objetivos del Examen Parcial

🎯 Enfoque de la Evaluación

Este examen parcial (20% de la nota) evalúa la comprensión integral de IoT cubierto en clases 1-9. Incluye: conceptos fundamentales, arquitectura, programación, protocolos y conectividad.

Este examen evalúa la comprensión integral de los conceptos fundamentales de IoT cubiertos en las clases 1-9. El estudiante deberá demostrar capacidad para:

  1. Conceptos fundamentales de IoT: Definir y explicar los pilares del IoT, su evolución y aplicaciones
  2. Arquitectura de sistemas IoT: Diseñar y justificar arquitecturas de 3 capas (Device/Edge/Cloud)
  3. Programación de microcontroladores: Interpretar código Arduino/ESP32 y seleccionar sensores/actuadores apropiados
  4. Protocolos de comunicación: Comparar HTTP vs MQTT, explicar QoS, seleccionar protocolos según caso
  5. Conectividad y redes: Diferenciar tipos de redes (LAN, WAN, LPWAN) y tecnologías (WiFi, LoRa, NB-IoT)
💻 Factibilidad Windows: Este examen es una guía teórica de estudio. No requiere instalación de software ni hardware específico. Todo el contenido se puede estudiar directamente en el navegador en Windows.

🅰️ Selección Múltiple

Pregunta 1 (2 puntos)

¿Cuál es la característica principal de MQTT?

  • Modelo request-response
  • Modelo publish-subscribe
  • Solo funciona con HTTP
  • Requiere conexión permanente a Internet
Respuesta Correcta: b)

MQTT utiliza el modelo publish-subscribe donde los clientes se suscriben a topics y reciben mensajes publicados en esos topics, sin necesidad de conocer al publicador.

Pregunta 2 (2 puntos)

Un sensor DHT11 se comunica mediante:

  • Protocolo I2C
  • Protocolo SPI
  • Pin digital con protocolo propietario
  • Conexión analógica
Respuesta Correcta: c)

El DHT11 utiliza un pin digital con su propio protocolo de comunicación (single-wire). Requiere la librería DHT para Arduino/ESP32.

Pregunta 3 (2 puntos)

¿Qué tecnología de red es más adecuada para sensores agrícolas a 5 km del gateway con batería que debe durar 5 años?

  • WiFi
  • LoRaWAN
  • Bluetooth
  • Zigbee
Respuesta Correcta: b)

LoRaWAN ofrece largo alcance (hasta 15 km rural), bajo consumo (años de batería) y es ideal para aplicaciones agrícolas donde no hay infraestructura eléctrica cercana.

🅱️ Verdadero/Falso

Preguntas de V/F (1 punto cada una)

Indique V si la afirmación es verdadera o F si es falsa:

V/F Afirmación Respuesta
1. ____ Edge Computing procesa datos más cerca de la fuente que Cloud Computing. V - Edge = local, Cloud = remoto
2. ____ El ESP32 tiene WiFi y Bluetooth integrado. V - Característica principal del ESP32
3. ____ MQTT usa el puerto 80 por defecto. F - MQTT usa 1883 (80 es HTTP)
4. ____ Un actuador captura datos del mundo físico. F - Los actuadores ejecutan acciones; los sensores capturan
5. ____ LoRaWAN es ideal para transmitir video en tiempo real. F - LoRaWAN tiene baja velocidad (ideal para datos pequeños)
6. ____ La pirámide DIKW representa la jerarquía Datos → Información → Conocimiento → Sabiduría. V - DIKW = Data, Information, Knowledge, Wisdom
7. ____ QoS 2 en MQTT garantiza entrega exactamente una vez. V - "Exactly once" = sin duplicados ni pérdidas
8. ____ Un gateway IoT solo sirve para conectar dispositivos a Internet. F - También traduce protocolos, filtra, agrega datos, etc.

✏️ Desarrollo Corto

Pregunta de Desarrollo (10 puntos)

Explique las diferencias entre los niveles de QoS en MQTT (QoS 0, 1 y 2). Para cada nivel, indique un caso de uso apropiado.

Respuesta Esperada (10 puntos)
QoS Significado Caso de Uso
QoS 0 "At most once" - El mensaje puede perderse. Fire and forget. Mínima latencia. Lecturas frecuentes de sensores de temperatura donde perder una lectura no es crítico.
QoS 1 "At least once" - El mensaje se entrega al menos una vez, puede duplicarse. Comandos importantes como encender una válvula de riego.
QoS 2 "Exactly once" - Entrega garantizada y única. Mayor overhead. Transacciones críticas como registros de facturación o alarmas de seguridad.

📊 Caso de Análisis

🌾 Caso: Sistema de Riego Inteligente (30 puntos)

Escenario: Una finca de café en la montaña requiere un sistema de riego automatizado con las siguientes características:

  • 20 sensores de humedad del suelo distribuidos en 5 hectáreas
  • 5 estaciones meteorológicas (temperatura, lluvia, viento)
  • 10 válvulas de riego controlables remotamente
  • Monitoreo desde una app móvil en tiempo real
  • Operación autónoma incluso sin conexión a Internet
  • La finca tiene conectividad celular intermitente

Preguntas del Caso:

Pregunta 1 (10 puntos)

Diseñe la arquitectura del sistema indicando:

  • Dispositivos en la capa de percepción
  • Componentes en la capa Edge/Gateway
  • Servicios en la capa Cloud
  • Protocolos de comunicación entre capas
Respuesta Esperada
  • Percepción: Sensores de humedad capacitivos, estaciones meteorológicas con sensores DHT22 y pluviómetros, válvulas motorizadas con actuadores, microcontroladores ESP32 en cada nodo.
  • Edge: Gateway LoRaWAN (como Dragino o RAK) que recibe datos de sensores remotos, Raspberry Pi para procesamiento local, almacenamiento buffer para cuando no hay Internet.
  • Cloud: Plataforma IoT (AWS IoT o similar), base de datos histórica, servidor de aplicación para la app móvil, dashboard web.
  • Protocolos: LoRaWAN (sensores al gateway), MQTT (gateway a cloud), HTTP/REST (API a app móvil).

Pregunta 2 (10 puntos)

Justifique la selección del protocolo de comunicación para los sensores de humedad. ¿Por qué no usar WiFi o celular directamente?

Respuesta Esperada

LoRaWAN es la mejor opción porque:

  • Alcance: Los sensores están a 5 hectáreas (500m x 100m), WiFi no alcanza esas distancias sin repetidores.
  • Batería: Los sensores deben operar con batería por años; LoRaWAN tiene muy bajo consumo vs WiFi/celular.
  • Costo: No requiere plan de datos celular para cada sensor.
  • Velocidad de datos: Los sensores de humedad envían pocos bytes cada hora; LoRaWAN es suficiente.
  • Contra WiFi: WiFi tiene alto consumo, menor alcance y requiere infraestructura de energía.
  • Contra celular: Costos de plan de datos, mayor consumo, puede ser excesivo para datos simples.

Pregunta 3 (10 puntos)

Explique cómo manejaría la operación sin conexión a Internet. ¿Qué componentes y lógica se requieren?

Respuesta Esperada
  • Gateway Edge autónomo: Raspberry Pi o similar ejecutando Node-RED o código Python localmente.
  • Lógica de riego local: Reglas programadas en el gateway (ej: "si humedad < 30% y no llovió hoy, abrir válvula 5 min").
  • Buffer de datos: Almacenar lecturas en SD card o SQLite mientras no hay conexión.
  • Sincronización: Cuando regresa Internet, enviar datos históricos a la nube.
  • Modo offline: App móvil puede conectarse directamente al gateway por Bluetooth o WiFi local si está cerca.
  • QoS MQTT: Usar QoS 1 para comandos importantes que deben ejecutarse cuando regrese la conexión.

🔑 Conceptos Clave para Repasar

🔧 Dispositivos

Arduino UNO/Nano

  • Microcontrolador ATMega328P
  • Flash: 32KB, SRAM: 2KB
  • Voltaje: 5V lógica
  • Pines: 14 digitales, 6 analógicos
  • No tiene WiFi nativo

ESP32

  • Dual-core Xtensa LX6
  • WiFi 802.11 b/g/n
  • Bluetooth 4.2 + BLE
  • Flash: 4MB típico
  • Voltaje: 3.3V (¡cuidado!)
  • ADC: 12 bits (0-4095)

Sensores Comunes

  • DHT11: Temp 0-50°C (±2°C), Hum 20-80% (±5%)
  • DHT22: Mayor precisión y rango
  • HC-SR04: Ultrasónico 2cm-4m
  • PIR: Infrarrojo pasivo (movimiento)
  • LDR: Fotorresistencia (luz)

Actuadores

  • LED: Indicador simple
  • Relé: Control ON/OFF AC/DC
  • Motor DC: Requiere driver (L298N)
  • Servo: Posición angular precisa
  • Válvula solenoide: Control de fluidos

🌐 Redes

Tecnología Alcance Velocidad Consumo Uso Ideal
WiFi ~50m Alta (Mbps) Alto Dispositivos conectados, video
Bluetooth ~10m Media Bajo Wearables, control cercano
LoRaWAN ~15km rural Muy baja (kbps) Muy bajo Sensores agrícolas, remotos
NB-IoT Cobertura celular Baja Bajo Smart cities, medidores

📡 Protocolos

HTTP (REST)

  • Modelo: Request-Response
  • Puerto: 80 (443 HTTPS)
  • Overhead: Alto (headers)
  • Ideal: APIs web, GET/POST
  • Ejemplo: HTTP GET /api/sensor/1

MQTT

  • Modelo: Publish-Subscribe
  • Puerto: 1883 (8883 TLS)
  • Overhead: Bajo
  • Ideal: IoT, mensajes pequeños
  • Topics: casa/sensor/temperatura

MQTT QoS

  • QoS 0: At most once
  • QoS 1: At least once
  • QoS 2: Exactly once
  • Mayor QoS = más overhead
  • Elegir según criticidad

Wildcards MQTT

  • + : Un solo nivel
    casa/+/temperatura
  • # : Múltiples niveles
    casa/sensor/#
  • # debe ir al final
  • + puede ir en cualquier nivel

⚡ ESP32 ADC

  • Resolución: 12 bits
  • Rango digital: 0 - 4095
  • Voltaje de referencia: 0 - 3.3V
  • Fórmula de conversión:
voltaje = (lectura_ADC / 4095.0) * 3.3;

🌡️ DHT11 Especificaciones

Parámetro Rango Precisión
Temperatura 0 - 50°C ±2°C
Humedad 20 - 80% RH ±5% RH
Tasa de muestreo 1 lectura/segundo máximo

📏 Sensor Ultrasónico HC-SR04

  • Rango: 2 cm - 400 cm (4 metros)
  • Precisión: ±3 mm
  • Fórmula de distancia:
// Velocidad del sonido = 343 m/s (aprox 29.1 µs/cm)
distancia_cm = (duracion_pulso_us / 2) / 29.1;

// O equivalente:
distancia_cm = duracion_pulso_us * 0.017;
