E1: Investigación Técnica (15%) - 23 de febrero de 2026

Propósito: Evaluar la capacidad de investigación y diseño de arquitectura IoT para el proyecto SMAI.

Formato: Documento técnico (PDF) con diagramas de bloques y justificación de selección de hardware.

Criterios de Evaluación

Criterio Alto (5.0-4.0) Medio (3.9-3.0) Bajo (2.9-1.0)
Arquitectura del Sistema Diagrama de bloques claro y completo (Sensores, Microcontrolador, Red, Nube). Diagrama aceptable pero faltan componentes o flujos de datos. Sin diagrama o diagrama incoherente.
Justificación de Hardware Sustenta técnicamente la elección de ESP32 y sensores específicos para el caso de uso. Justificación genérica sin entrar en detalles técnicos de voltajes o protocolos. Sin justificación técnica real.
Investigación de Protocolos Compara y elige correctamente el protocolo de red (WiFi/LoRa) según el entorno. Menciona protocolos pero no justifica su idoneidad para el proyecto. Desconocimiento de protocolos aplicables.
Formato Técnico Documento profesional, ortografía perfecta y uso de terminología técnica correcta. Documento aceptable con errores menores de formato. Documento desordenado o lenguaje no técnico.

E2: Prototipo Sensórico (15%) - 9 de marzo de 2026

Propósito: Validar la lectura de variables físicas y control de actuadores en local.

Formato: Demostración en clase (Físico o Wokwi) del circuito funcionando.

Criterios de Evaluación

Criterio Alto (5.0-4.0) Medio (3.9-3.0) Bajo (2.9-1.0)
Lectura de Sensores Lectura precisa de temperatura, humedad (DHT22) y luz (LDR) mostrada por serial. Lectura inestable o solo de un sensor. No logra leer los sensores.
Control de Actuadores LEDs reaccionan correctamente a los cambios en los sensores (lógica local). Los actuadores funcionan pero la lógica es errática. Actuadores no funcionan.
Estructura del Código Código modular, usa constantes, sin delays bloqueantes innecesarios. Código funcional pero desordenado (Spaghetti code). Código con errores de compilación o incomprensible.
Montaje (Gemelo Digital) Uso correcto de protoboard o link de Wokwi perfectamente organizado. Conexiones confusas o cables sueltos en el simulador. Cortocircuitos o montaje erróneo.

E3: Software IoT (20%) - 16 de marzo de 2026

Propósito: Evaluar la implementación de conectividad IP y reporte a la nube.

Formato: Código fuente (.ino) + Dashboard público en ThingSpeak.

Criterios de Evaluación

Criterio Alto (5.0-4.0) Medio (3.9-3.0) Bajo (2.9-1.0)
Gestión WiFi Conexión exitosa, manejo de reconexión y visualización de IP en serial. Se conecta pero no maneja pérdida de señal. No logra conectar el ESP32 a la red.
Protocolo HTTP/MQTT Implementación correcta del protocolo para enviar datos a la nube. Envía datos pero con errores de formato o latencia alta. No envía datos a internet.
Dashboard Cloud Visualización clara de datos históricos y en tiempo real en ThingSpeak/Adafruit. Dashboard básico sin etiquetas ni unidades claras. Sin visualización en la nube.
Seguridad Básica Uso de archivos de cabecera para credenciales o manejo seguro de API Keys. API Keys en el código principal (Hardcoded). Exposición innecesaria de credenciales críticas.

E4: Firmware + FastAPI + Base de Datos (15%) - 20 de abril de 2026

Propósito: Cimentar el proyecto con firmware mejorado, API propia y base de datos funcionando.

Formato: Informe técnico (PDF) + código fuente ZIP. Todo lo construido en E4 es la base para E5 y E6.

Criterios de Evaluación

Criterio Alto (5.0-4.0) Medio (3.9-3.0) Bajo (2.9-1.0)
Firmware mejorado Usa millis(), máquina de estados e histéresis correctamente. Código limpio y funcional. Usa millis() pero con errores menores en estados o histéresis. Usa delay() bloqueante o no implementa máquina de estados.
Envío de datos (HTTP/MQTT) ESP32 envía JSON estructurado de forma estable a la API o broker MQTT. Envía datos pero con formato incorrecto o conexión intermitente. No logra enviar datos desde el ESP32.
API FastAPI / MQTT 3 endpoints funcionando (POST /datos, GET /datos, GET /datos/latest) o subscriber MQTT activo. Swagger/docs accesible. API básica funcionando pero le faltan endpoints o tiene errores de CORS. API no responde o no tiene los endpoints mínimos requeridos.
Base de datos Tabla creada correctamente, datos insertados desde ESP32 y consultas funcionando. Tabla creada pero con errores en tipos de datos o inserciones. No hay base de datos o no se persisten datos.
Calidad del informe Informe claro con diagramas, evidencias (screenshots de Swagger, BD, logs) y código documentado. Informe completo pero con poca evidencia o explicaciones superficiales. Informe incompleto o sin evidencias de funcionamiento.

E5: Demo de Integración Total + Visualización (15%) - 4 de mayo de 2026

Propósito: Demostrar en clase el sistema completo funcionando de punta a punta.

Formato: Demo en vivo en clase + código fuente ZIP en Canvas. Se construye sobre E4 — mismo firmware, API y BD.

Criterios de Evaluación

Criterio Alto (5.0-4.0) Medio (3.9-3.0) Bajo (2.9-1.0)
Comunicación ESP32→API Envío estable de JSON, intervalo definido y conexión WiFi confiable durante la demo. Envía datos pero con caídas ocasionales o latencia alta. No logra comunicación estable entre ESP32 y API.
API funcional con BD Endpoints operan correctamente, datos persistentes y historial disponible (SQLite/MySQL). API funciona pero con errores en consultas o BD incompleta. API o BD no funcionan durante la demo.
Visualización de datos Dashboard propio (HTML+JS), Grafana o interfaz funcional mostrando datos en tiempo real o históricos. Visualización básica o que no se actualiza correctamente. Sin visualización de los datos.
Funcionamiento en vivo Demo en clase sin fallos mayores; el sistema opera de forma continua durante la presentación. Demo funciona pero requiere reinicios o ajustes durante la clase. Demo falla o no se puede presentar en clase.
Coherencia con E4 Reutiliza y mejora el trabajo de E4 sin reconstruir desde cero. Reutiliza parte de E4 pero cambia mucho la arquitectura. Sistema completamente diferente al entregado en E4.

E6: Sustentación Final del Proyecto IoT (20%) - 25 de mayo de 2026

Propósito: Evaluación integral del sistema completo mediante sustentación oral y demo en vivo.

Formato: Pitch de 10-15 min + Demo técnica en vivo + defensa de código. Se demuestra todo lo construido en E4 y E5 (FastAPI o MQTT + BD).

Criterios de Evaluación

Criterio Alto (5.0-4.0) Medio (3.9-3.0) Bajo (2.9-1.0)
Funcionamiento en vivo Todo el sistema opera durante la sustentación: ESP32, API/BD y visualización sin fallos. Funciona pero requiere reinicios o ajustes durante la demo. El sistema falla durante la sustentación o no está terminado.
Explicación del flujo de datos Explica con claridad técnica cada capa: Firmware → API → BD → Visualización. Explica el flujo pero con imprecisiones técnicas o saltos. No logra explicar cómo viajan los datos de punta a punta.
Dominio del código Responde con seguridad preguntas sobre millis(), estados, endpoints, BD y CORS. Responde algunas preguntas pero con dudas en detalles técnicos. No domina el código ni puede defender decisiones técnicas.
Visualización / dashboard Interfaz funcional, útil y actualizada con datos reales de la BD propia. Visualización básica o con datos de prueba / no actualizados. Sin visualización o dashboard inoperante.
Presentación general Tiempo bien manejado, organización clara, actitud profesional y participación de todos. Desorganizado o algunos integrantes no participan. Mala presentación o actitud poco profesional.
📌 Políticas Generales:
  • Todas las evaluaciones son obligatorias
  • No se aceptan entregas tardías sin justificación válida
  • Las entregas técnicas se validan en laboratorio o simulador
  • Los prototipos requieren funcionamiento del hardware real o virtual
  • Los informes técnicos deben ser originales (política anti-plagio)
