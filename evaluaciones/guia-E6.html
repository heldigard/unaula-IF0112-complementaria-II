Fase 6: Demo en vivo de ESP32 → API → BD → Visualización

Nota importante

E6 es la entrega final del proyecto, presentada mediante sustentación oral con demo en vivo. Se demuestra todo lo construido en E4 y E5.

Pueden usar FastAPI + BD o MQTT + BD como flujo de datos principal.

Objetivo

Demostrar en una sustentación oral que dominan el proyecto completo: el ESP32 envía datos, la API los procesa, la base de datos los almacena y la visualización los presenta. Se evaluará el funcionamiento en vivo y la capacidad de explicar cada capa técnica.

Prerrequisitos (Integración E4-E5)

Para la sustentación final debes presentar:

  • E4: Firmware con millis(), máquina de estados e histéresis + API básica + BD funcionando.
  • E5: Sistema integrado con visualización operativa.
  • Producto físico encapsulado y listo para enchufar.

Nota: E6 es la entrega final con sustentación de todo el trabajo anterior. Se perfecciona y encapsula lo existente. Flujo principal puede ser FastAPI o MQTT.

Requisitos de la Sustentación

  • Demo en vivo del sistema completo:
    • Encender el ESP32 y mostrar que se conecta a WiFi.
    • Levantar la API en el PC (o mostrar que ya está corriendo).
    • Verificar que los datos llegan a la base de datos.
    • Mostrar la visualización actualizándose con datos reales.
  • Explicación del flujo de datos:
    • Capa 1 - Firmware: cómo lee sensores, gestiona estados y envía JSON.
    • Capa 2 - API: qué hace cada endpoint y por qué se eligió FastAPI (o Flask/MQTT).
    • Capa 3 - Base de datos: estructura de la tabla y cómo consultar los datos.
    • Capa 4 - Visualización: cómo muestra los datos al usuario final.
  • Datos históricos reales:
    • La BD debe contener datos reales acumulados, no inventados.
    • Se puede mostrar una consulta SQL o el historial en la visualización.
  • Responder preguntas técnicas del profesor sobre:
    • Uso de millis() vs delay().
    • Transiciones de la máquina de estados y la histéresis.
    • Formato JSON enviado por el ESP32.
    • Funcionamiento de los endpoints POST /datos, GET /datos y GET /datos/latest.
    • Schema de la base de datos y tipo de cada campo.
    • Por qué habilitaron CORS y qué problema resuelve.
    • Diferencias entre HTTP y MQTT en su proyecto.
  • Plataformas IoT externas (opcional):
    • ThingSpeak, Ubidots u otras plataformas ya no son requisito en E6.
    • Si las usan como complemento, se valora, pero la evaluación se centra en su propio sistema API+BD.

Estructura sugerida de la sustentación (10-15 min)

  1. Presentación del problema y solución (2 min): Qué monitorean, por qué y cómo lo resolvieron.
  2. Demo en vivo del sistema completo (5 min): Encender, enviar, almacenar y visualizar datos en tiempo real.
  3. Explicación técnica del flujo de datos (3 min): Firmware → API → BD → Dashboard.
  4. Preguntas del jurado (3-5 min): Responder con claridad y mostrar el código si es necesario.

Lista de Verificación Final - Pre-Sustentación

  • ☐ El dispositivo enciende automáticamente al conectar USB (sin depender de la laptop si es posible)
  • ☐ Se conecta a WiFi en menos de 30 segundos
  • ☐ Los LEDs muestran el estado del sistema según la máquina de estados
  • ☐ La API está corriendo y responde en /docs
  • ☐ La BD tiene datos históricos reales
  • ☐ La visualización muestra datos actualizados
  • ☐ El producto está encapsulado (caja/gabinete)
  • ☐ No hay cables sueltos (usar amarras)
  • ☐ Repositorio GitHub con código y README
  • ☐ Presentación tipo pitch preparada (10-15 min)
